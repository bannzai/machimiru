# 軸の追加リクエストから軸を足す手順

チャットで入れた条件のうち registry (`src/lib/axes.ts`) に無い軸の条件は、ブラウザに軸の追加のリクエストとして記録される (`documents/PROJECT.md`「文章の判定」)。この文書は、そのリクエストを agent が軸にする手順を定める。チャットの時点で公開統計を探して取り込むのは、応答時間・利用条件と列の解釈の自動判断の信頼性・費用の点で成り立たないため、軸を足すのは agent の作業にした (#26)。

## 依頼の受け方

bannzai は、トップページの「リクエスト済みの条件」の「軸の追加の依頼文をコピー」で、次の形の文をコピーして `claude` の対話に貼る。

```text
documents/add-axis.md の手順で、次の軸の追加リクエストを軸にして
- 軸の候補名: 治安 / 条件の文: 犯罪率が低い場所
```

軸の候補名は文章の判定が振り分けた先 (`src/lib/conditionClassification.ts` の `unsupportedAxisCandidates` か「その他」) で、確定した軸の名前ではない。条件の文から軸と条件の名前を決め直してよい。リクエスト 1 件ごとに下の 4 手順を行い、軸ごとに 1 つの PR にする。

ブラウザに記録したリクエストは軸を足した後も消えず、コピーのたびに全件が入る。registry に既にある軸・条件と、`unavailableReason` を登録済みの軸のリクエストは、対応済みとして飛ばし、どれを飛ばしたかを返答に書く。

## 1. 点か面かを決める

条件の文が何で判定できるかで、判定器の種類 (`ConditionEvaluator`) を決める。判定器の仕組みは `documents/PROJECT.md`「判定器と、現在の軸」。

- 点: 施設の位置で判定できる条件 (「〜が近い」「〜が多い」)。例: コワーキングが近い・小児科が近い
- 面: 区市町村ごとの統計で判定できる条件 (率・件数・金額)。例: 犯罪率が低い・保育園に入りやすい
- 点の施設の評判・口コミ・営業時間のように、施設の位置や統計の値に無い性質を求める条件は、どちらでも判定できない見込みが高い。手順 2 で出典が見つからなければ手順 4 に進む

既存の軸の条件として足せる時 (「小児科が近い」に対する「歯科が近い」など) は、新しい軸を作らず既存の軸に条件を足す。

## 2. 出典を探し、利用条件を確かめる

次の順で探し、最初に条件を満たす出典を使う。

1. `public/data/` の既存データ (`public/data/tokyo/municipalities.json`・`facilities.geojson`・境界データ)。既にある値から計算できるなら新しい出典は要らない
2. 点: OpenPOI API の名前検索 (`documents/PROJECT.md`「データの出典」の行と「実装の前提になる調査結果」)。施設の種類で絞れないため、東京都内のいくつかの範囲で検索語ごとの件数と中身を実測し、検索語で足りるかを確かめる
3. 面: e-Stat API ( https://www.e-stat.go.jp/api/ )。e-Stat のユーザ登録で発行されるアプリケーション ID が要る (e-Stat API 利用規約 3 条 https://www.e-stat.go.jp/api/terms-of-use )。アプリケーション ID の発行・登録は外部サービスとの新しい連携に当たるため、初めて使う時は bannzai に確認する。ID はコードと生成データに書かず、取り込みの実行時に環境変数で渡す
4. 東京都オープンデータカタログサイト ( https://catalog.data.metro.tokyo.lg.jp/ )・警視庁など各機関のオープンデータ。カタログが機械からの取得を拒否する時は、データカタログ横断検索システム search.ckan.jp のメタデータで確かめる

候補ごとに、利用条件を一次情報 (提供元の利用規約・ライセンスのページ) で確かめる。確かめる項目は、二次利用 (加工して配信してよいか)・出典表示の文言・商用利用の可否。確かめた URL と日付は、使う時は `documents/PROJECT.md`「データの出典」の表に、使わない時も同じ表に「使えない」と理由つきで書く (同表の「保育サービスの利用率」の行が例)。API 経由で取得する出典は、データ自体の利用条件に加えて API の利用規約も確かめる (e-Stat API は利用規約 7 条でサービスへのクレジット表示を求め、文言は https://www.e-stat.go.jp/api/api-info/credit 。2026-10-05 確認)。

## 3. 取り込み・テスト・表示を揃えて PR にする

1 つの PR に次を揃える。足し方の細部は `documents/PROJECT.md`「軸の足し方」と `.claude/rules/external-data-attribution.md` に従う。

- 取り込み: 取得したファイルから `public/data/` のデータを生成するスクリプト。`make data-tokyo` (`scripts/data/tokyo/generate.ts`) と同じ形で、出典を `src/lib/tokyoData/sources.ts` に持ち、生成したファイルの `sources` に書き込む。生成データは commit する。ブラウザから検索のたびに呼ぶ API (OpenPOI API など) を判定器にする時は、取り込みのスクリプトは要らない
- テスト: 取り込みの変換と値の計算のテスト、`src/lib/axes.test.ts` (4 段階すべてに区市町村が入る)、`src/lib/conditionClassification.test.ts` (条件の文がその軸の条件に判定される)
- `documents/PROJECT.md`: 「データの出典」の表の行と「判定器と、現在の軸」の表の行。出典ページ (`/sources/`) はこの表をビルド時に読むため、表に足せば表示される
- registry: `src/lib/axes.ts` の `axes` に軸か条件を 1 件足し、`unsupportedAxisCandidates` から同じ名前の候補を消す
- 画面の確認: `e2e/` に、足した軸のタブを開いた状態を撮る手順を足し、CI の `screenshot` job の撮影を目視で確かめる (`AGENTS.md`「検証方法」)
- この文書の「実例」に、出典の探し方と確かめた利用条件を足す

## 4. 出典が無い時は「判定できない軸」として登録する

出典が見つからない、または利用条件で使えない時は、`src/lib/conditionClassification.ts` の `unsupportedAxisCandidates` の候補に `unavailableReason` を書く。チャットはその軸の条件に「この軸は<理由>ため判定できません」と出し、軸の追加のリクエストとして記録しない。

- 候補が無い時は、`name`・`classifierDescription` (Jev に渡す英語の説明)・`keywords` (辞書による判定の語) と一緒に候補を足す。軸の候補を足すと Jev への質問が文ごとに 1 つ増える (`src/lib/conditionClassification.test.ts` の質問の数の検査を直す)
- 理由は「ため」に続く形で、何が無いかを書く (例: 口コミを二次利用できる公開データが無い)。探した出典と確かめた利用条件は、`documents/PROJECT.md`「データの出典」の表に「使えない」の行として書き、理由の根拠にする
- 後で使える出典が見つかったら、`unavailableReason` を消して手順 3 で軸を足す

## 実例

軸を足した PR・判定できない軸を登録した PR は、ここに出典の探し方と確かめた利用条件を足す。

- 保育サービスの利用率 (子育ての軸を作った時。#5・#7): 東京都「都内の保育サービスの状況について」の表を候補にしたが、東京都公式ホームページの「著作権・リンクについて」が無断の複製・転用を認めず、東京都オープンデータカタログサイトにも同じ表が無かった (search.ckan.jp で検索)。待機児童数は同じ値を持つこども家庭庁の PDL1.0 のデータに替え、利用率は計算しなかった。確かめた URL は `documents/PROJECT.md`「データの出典」の「保育サービスの利用率」の行
- 犯罪率 (#24)・コワーキング (#25): 各 issue の PR が足す
